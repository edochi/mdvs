# TODO-0200: Frontmatter-only edits never reach the search index

## Summary

Incremental `mdvs build` decides whether a file changed from a hash of its
**body** only, so editing just the frontmatter leaves the indexed frontmatter
stale. `search --where` then filters on old values until `build --force`.
Affects the released v0.8.5.

## Details

Found during TODO-0197 wave 7.5 review. `classify_files`
(`crates/mdvs/src/cmd/build/classify.rs`) computes
`content_hash(&file.content)`, and `ScannedFile::content` is the body without
frontmatter. A frontmatter-only change therefore classifies the file as
unchanged: no re-embed, and its file row (which carries the denormalised
frontmatter in the `data` struct column) is not rewritten.

Example: change `status: draft` to `status: published` in one file, run
`mdvs build`, then `mdvs search "..." --where "status = 'published'"` — the file
is missing from the results (and still matches `status = 'draft'`).

The existing test `incremental_frontmatter_only_change` covers the chunk-reuse
side (no re-embed for a frontmatter-only edit, which is the intended
optimisation) but never checks the stored frontmatter.

Design question for the fix: keep "frontmatter-only edit does not re-embed"
(embedding depends on the body only) but rewrite the file row. Options include a
second hash over the frontmatter that triggers a file-row update without
re-embedding, or always rewriting file rows (cheap compared with embedding).
Decide with the user. Regression test: frontmatter-only edit → build → `--where`
on the new value finds the file, on the old value doesn't.
