# TODO-0199: Incremental build panics in Lance after editing files

## Summary

An incremental `mdvs build` panics inside Lance after a short sequence of edits,
and every later build of that vault panics too until `build --force`. Affects
the released v0.8.5.

## Details

Found during TODO-0197 wave 7.5 while comparing build output before and after a
refactor. Reproduced on `main` (v0.8.5, `54ef3e0`) and on `feat/clippy-pedantic`
— not introduced by the cleanup.

Repro (mock embedder, so no model download — build the binary with
`--features testing-mocks`):

1. Copy `example_kb` to a temp dir, remove `.mdvs/`, and in `mdvs.toml` set
   `[embedding_model] provider = "mock"`, `name = "mock"`, `dim = 256`.
2. `mdvs build` → ok.
3. Add `new-note.md` (`# Drift\n\nCalibration drift notes added later.\n`) →
   `mdvs build` → ok.
4. Append a line to `new-note.md` → `mdvs build` → ok.
5. Append a line to `scratch.md` → `mdvs build` → **panic, exit 101**:

   ```
   thread 'main' panicked at lance-encoding-6.0.0/src/buffer.rs:290:9:
   the offset + length of the sliced Buffer cannot exceed the existing length
   ```

6. Any further build (e.g. after deleting `lab-values.md`) panics the same way.

Editing `scratch.md` alone on a fresh index does not panic; the sequence
matters. Suspect the incremental write path from TODO-0173 Phase B
(`delete("file_id IN (...)")` + `add` + `replace_schema_metadata` +
`optimize(All)`) leaving the dataset in a state Lance's reader mis-slices —
possibly related to the v2.2 storage version from TODO-0169.

To do:

- Minimise the repro (which of delete / add / optimize triggers it; does it need
  the earlier add+edit?). Check whether it reproduces with the real model2vec
  provider.
- Check Lance / lancedb upstream issues and whether a newer release fixes it.
- Add a regression test that runs the sequence against a temp vault and asserts
  every build succeeds and the index stays readable (`info`, `search`).
- A panic inside a dependency should not abort mdvs: even before the root fix,
  consider whether the write path can detect a corrupt dataset and fall back to
  a full rebuild with a clear message.
