# TODO-0204: Search loads the embedding model on every run when the vault has empty-body files

## Summary

With `auto_build` on (the default), every `mdvs search` loads the embedding
model if the vault contains any file with an empty body, even when nothing
changed and even in `--mode fulltext`. On the K8s docs corpus that is ~560 ms
per search with the default model, about half the total search time.

## Details

Found on 2026-10-19 while benchmarking TODO-0203. The K8s docs corpus (1,669
files) has 67 empty-body files (Hugo `_index.md`).

Chain:

1. `search` → `auto_build_step` → `build_core`.
2. `classify_files` (`crates/mdvs/src/cmd/build/classify.rs`) puts the 67 files
   in `needs_embedding`: they have no rows in the index, so they always look
   new.
3. `load_embedder_step` (`crates/mdvs/src/cmd/build/embed.rs`) loads the model
   whenever `needs_embedding` is non-empty.
4. The files produce zero chunks, the write planner skips the write (TODO-0173
   Phase A), nothing records them as indexed, and the next search repeats it.

TODO-0167 skips the model load for fulltext in the search step itself; this load
comes from the auto-build step before it, so 0167's saving is lost on any vault
with an empty-body file. The cost was ~20–40 ms with the old default model and
became ~560 ms when the default moved to `potion-multilingual-128M` (TODO-0205).

Fix options (decide with the user):

- **Chunk before loading the model.** Load only when at least one file produces
  a chunk. Smallest change; the empty files are still re-classified (cheap) on
  every build.
- **Record empty-body files as indexed.** Store them (file row with no chunks,
  or the hash in build metadata) so they classify as unchanged. Fixes the root
  cause and overlaps with TODO-0201, which needs to know whether a file had
  prior rows.

Regression test: vault with one empty-body file, build, then a second build (or
`search --mode fulltext` with auto-build) must not load the model (assert the
`LoadModel` step is skipped).
