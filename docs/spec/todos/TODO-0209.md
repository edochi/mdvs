# TODO-0209: Backend comparison harness, and Turso as a candidate backend

## Summary

Build a harness that runs the same storage and search workload against different
backends on the same data, and use it for a first assessment of
[Turso](https://github.com/tursodatabase/turso) (SQLite-compatible, in Rust)
against LanceDB. Assessment only: no change to mdvs's backend.

## Details

### Why

LanceDB has cost real work: a panic on filtering `Array(Float)` (TODO-0159), a
panic on incremental builds (TODO-0199), and in TODO-0203 a lancedb release
range that didn't compile, a leftover `__manifest` directory and BM25 score
drift. Lance plus DataFusion also make up most of the 242 MB binary (TODO-0206).
Turso offers SQL-native filtering, BM25 full-text search (built on Tantivy) and
vector functions in one engine, but as of 2026-10 its full-text search is
experimental and it has no approximate vector index (exact search only).

### Harness design

One standalone `rust-script` per backend, so each binary holds only its own
engine (honest size and startup numbers) and dependency versions never clash:

- `scripts/bench_backend_export.rs` reads a built mdvs index
  (`<vault>/.mdvs/index.lance`) and writes the dataset every backend loads:
  `chunks.jsonl` (chunk id, file id, path, text, frontmatter JSON, embedding)
  and `queries.jsonl` (query text, mode, optional equality filter, query
  embedding from the vault's configured model).
- `scripts/bench_backend_<name>.rs <dataset> <workdir>` runs the workload and
  prints one JSON result: load time (insert and index build), open time,
  incremental update time (delete and re-insert the chunks of 50 files), disk
  size, executable size, and per query p50 / p95 latency over N warm runs plus
  the top-10 chunk ids.
- `docs/benchmarks/backends.py` runs the export once, runs each backend script
  and prints the comparison, including top-10 overlap between backends (exact
  vector search is the ground truth for approximate-index recall).

Each backend mirrors what mdvs does: Lance gets an FTS index and, from 10,000
rows, an IVF-PQ cosine index; hybrid uses Lance's RRF reranker. Backends without
native hybrid search fuse vector and BM25 results with RRF in the script.
Filters are given as field/value pairs and each backend translates them (Lance:
`data.<field> = '<value>'`; SQL: `json_extract`).

Dataset: the kubernetes/website docs corpus (1,669 files, ~22,700 chunks, so the
approximate-index path is exercised) and `example_kb`, with the query sets from
`docs/benchmarks/run.py`.

### Turso questions to answer

- Load, open, query and incremental-update times against Lance, per mode.
- Exact-scan vector latency at ~23k chunks against Lance's IVF-PQ, and IVF-PQ's
  top-10 overlap with exact search.
- BM25 result overlap with Lance's full-text search.
- Disk size and executable size.
- Whether frontmatter filters (scalar, nested, `Array(...)`) translate cleanly
  to SQL.
- Re-assess when Turso ships an approximate vector index and its full-text
  search leaves experimental.
