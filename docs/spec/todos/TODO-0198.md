# TODO-0198: Search results are nondeterministic when scores tie

## Summary

When several files tie on score, `mdvs search` can return a different set or
order of results from one run to the next with the same index and query. Hybrid
search hits this routinely (RRF scores tie often); any mode can hit it. Make
result order deterministic.

## Details

Found during TODO-0197 wave 7.3 while diffing search output before and after a
refactor: `search --mode hybrid --limit 3` on a mock-embedder copy of
`example_kb` differed between two runs of the **unchanged** binary. The third
hit tied on RRF score (0.017) with other files, and which tied file survived
`--limit` changed between runs.

Cause: `dedupe_best` in `crates/mdvs/src/index/backend/search.rs` collects the
best hit per file into a `HashMap`, then

```rust
let mut hits: Vec<SearchHit> = best.into_values().collect();
hits.sort_by(|a, b| b.score.partial_cmp(&a.score).unwrap_or(Ordering::Equal));
hits.truncate(limit);
```

`HashMap` iteration order is randomized per process, and the sort is by score
only, so tied hits keep that random order and `truncate` keeps an arbitrary
subset.

Proposed fix: add a deterministic tiebreak after score — by `filename`
(`.then_with(|| a.filename.cmp(&b.filename))`).

Also check, as part of the same fix:

- **Within-file ties.** When two chunks of the same file tie on score, which
  chunk is kept as the file's best hit (and therefore `start_line` / `end_line`
  / `chunk_text`) depends on Lance batch order. Decide whether that needs a
  tiebreak too (e.g. lowest `start_line`).
- **Candidate set.** `run_query` asks Lance for `k` candidates before dedupe; if
  Lance itself cuts a tie at `k`, the candidate set can vary before mdvs sees
  it. Determine whether that can happen and whether `k` needs headroom.
- **NaN scores.** `partial_cmp(..).unwrap_or(Equal)` makes a NaN compare equal
  to everything; check whether scores can be NaN, and if not, whether
  `total_cmp` is the clearer choice.

Test: a fixture where more files tie on score than `--limit` keeps, asserting
the same hits in the same order across repeated runs. Show red-then-green: it
must fail (at least intermittently, or deterministically by seeding the
`HashMap` order) without the tiebreak.
